# Release artifact naming — Private Ballot

This document defines the **canonical, release-facing filenames** for future
Private Ballot release assets and the exact mapping from the raw names the
Tauri bundler emits.

It applies to **future releases only**. The published **v0.1.0** GitHub release
assets and their checksums are frozen and must not be renamed.

## Why a staging rename step

Filenames are generated by the Tauri bundler from each app's `productName`,
`version`, and target architecture. Those raw names contain **spaces** and use
**inconsistent architecture tokens** across formats (`x64`, `amd64`, `x86_64`,
`aarch64`), which makes it hard for a user to tell which download matches their
operating system and CPU.

We do **not** change `productName`, bundle identifiers, executable names,
package IDs, protocol identifiers, or persisted paths to fix this. Instead, a
**release staging step renames the built artifacts** to the canonical scheme
below immediately before checksums are generated and assets are uploaded. The
macOS qualification workflow
([.github/workflows/macos-qualification.yml](../../.github/workflows/macos-qualification.yml))
already performs this rename for its `.dmg` outputs; Windows and Linux release
staging (currently manual) must apply the same mapping.

## Canonical scheme

```
private-ballot-v<VERSION>-<os>-<arch>.<ext>                 # Organizer
private-ballot-load-tester-v<VERSION>-<os>-<arch>.<ext>     # Load Tester
```

Rules:

- **No spaces**; lowercase ASCII with hyphen separators (file extensions keep
  their conventional case, e.g. `.AppImage`).
- **Application explicit** — Organizer has no suffix; the Load Tester carries
  `-load-tester`.
- **Version explicit** — `v<VERSION>` (e.g. `v0.1.0`).
- **Operating system explicit** — `windows`, `linux`, or `macos`.
- **Architecture explicit** — `x86_64` or `aarch64`. Do **not** ship
  release-facing `x64`, `amd64`, or `en-US` tokens; normalize them all to
  `x86_64` (and `aarch64` for Apple Silicon).
- The Windows NSIS installer keeps a `-setup` marker to distinguish it from the
  `.msi`.

## Source → canonical mapping

`<VERSION>` is the app version from its `tauri.conf.json` (e.g. `0.1.0`).

### Organizer (`gui/`, productName "Private Ballot")

| Format | Raw Tauri name | Canonical name |
| --- | --- | --- |
| Windows MSI | `Private Ballot_<VERSION>_x64_en-US.msi` | `private-ballot-v<VERSION>-windows-x86_64.msi` |
| Windows NSIS | `Private Ballot_<VERSION>_x64-setup.exe` | `private-ballot-v<VERSION>-windows-x86_64-setup.exe` |
| Linux DEB | `Private Ballot_<VERSION>_amd64.deb` | `private-ballot-v<VERSION>-linux-x86_64.deb` |
| Linux RPM | `Private Ballot-<VERSION>-1.x86_64.rpm` | `private-ballot-v<VERSION>-linux-x86_64.rpm` |
| Linux AppImage | `Private Ballot_<VERSION>_amd64.AppImage` | `private-ballot-v<VERSION>-linux-x86_64.AppImage` |
| macOS DMG (Apple Silicon) | `Private Ballot_<VERSION>_aarch64.dmg` | `private-ballot-v<VERSION>-macos-aarch64.dmg` |
| macOS DMG (Intel) | `Private Ballot_<VERSION>_x64.dmg` | `private-ballot-v<VERSION>-macos-x86_64.dmg` |

## Checksums

Generate `SHA256SUMS` **after** the rename, so the manifest lists exactly the
canonical names users download. The macOS workflow already orders the steps this
way (normalize → checksum → upload).

## Architecture reference for users

- Windows / Linux `x86_64` — standard 64-bit desktops and laptops.
- macOS `aarch64` — Apple Silicon (M1/M2/M3/M4 and later).
- macOS `x86_64` — Intel-based Macs.
