## 2. Purpose

Slice 5A3 builds the first desktop GUI shell on top of gui-core, exactly as
staged by ADR-0007: **Tauri 2 + React + TypeScript + Vite**, gui-core as the
only backend interface, no local HTTP server, no shelling out to binaries,
no CLI stdout parsing, no protocol logic in JavaScript, no secrets in the
frontend. This slice is the application framework: navigation, themes,
branding, dashboard cards, and placeholder flows wired to real gui-core DTOs
where available. It redesigns no backend logic.

## 5. Theme system

- Token scales in `gui/src/styles/global.css` are the official Tari brand
  scales (§6). Light theme and dark theme are full token sets keyed off
  `data-theme` on the document root; `color-scheme` is set per theme so
  native form controls match.
- `ThemeProvider` resolves `system` via `prefers-color-scheme` with a live
  change listener, plus a manual `light`/`dark` override persisted in
  `localStorage` (theme preference only; not a secret). The toolbar toggle
  flips the resolved theme; Settings offers all three modes as a radio
  group.
- Contrast: brand purple for filled primary actions is `#813BF5` with white
  text (≈5.4:1) in both themes; status colors use the darker 700-step tints
  as text on light surfaces and the lighter 200/300-step tints as text on
  dark surfaces (WCAG-friendly combinations); secondary text uses the
  official grey steps. Branding color is confined to the toolbar brand,
  primary buttons, selected navigation, links, focus rings, and accent
  pills — the interface is otherwise neutral surface greys.

## 8. Screens

- **Home** — dashboard cards only: Current election, Election lifecycle,
  Manifest hash, Archive hash, Anchor status, Verification status, Recent
  actions (session-scoped log). Empty states show no mock data.
- **Create Election** — placeholder; a ballot-type selector (Candidate
  election / Governance proposal / Ballot measure) drives the example layout
  and vocabulary from the same neutral option-set model. Explains the
  three-artifact package.
- **Manage Election** — step cards Review/Freeze → Open Voting → Ballot
  intake → Close Voting → Tally → Verify → Archive → Anchor. Artifact
  loading, all four lifecycle transitions, ballot intake, tally, and archive
  writing call **real** gui-core commands and render real DTOs; the anchor
  step is a placeholder pointing at the inspection screens.
- **Vote** — placeholder stepper: Import credential → Load election →
  Review ballot → Cast ballot → Export ballot package → Confirmation.
  Review renders the real loaded option set with ballot-type vocabulary;
  credential handling repeats the ADR-0007 constraints (import-only,
  per-session, never persisted; key generation deferred to its own reviewed
  crypto slice).
- **Archive** — runs the real `verify_archive_directory_v1` replay verifier
  and renders manifest hash, registry/catalog file checks, ballot options
  with recomputed tallies, accepted/rejected counts, archive hash vs
  recomputed hash, and the verification status.
- **Anchor** — real Phase 4 inspection wrappers: config inspection (network,
  digests, fee parameters) and snapshot inspection (phase, terminal status,
  transaction id, poll counters, walletd/receipt tables). No walletd
  redesign; no network contact.
- **Evidence** — real `inspect_anchor_evidence_v1` rendering: final status,
  receipt source, phase, all digests, transaction id, ledger position,
  snapshot digest, and the fixed non-binding human-review summary.
- **Settings** — theme (automatic/light/dark), data directory, default
  export directory, developer diagnostics toggle. No secrets fields exist.
- **About** — identity, version, branding attribution, architecture
  boundary, non-production notice.

**Ballot types:** `ballot/ballotTypes.ts` defines the presentation model
(candidate / governance-proposal / ballot-measure) over the neutral option
set. The current manifest format carries only `NON_BINDING_APPROVAL_PILOT`,
so the UI never infers candidacy; neutral vocabulary ("ballot options",
"option set") is the default and "candidate set" appears only when naming
the canonical artifact itself.

## 9. Accessibility

- Keyboard navigation: every control is a native focusable element; skip
  link to main content; navigation items are real buttons with
  `aria-current`.
- Visible focus: 2px `var(--focus-ring)` outline with offset on
  `:focus-visible`, in both themes.
- Scalable typography: rem-based throughout; no fixed pixel font sizes on
  text content.
- High contrast: contrast-checked token pairings (§5); status is never
  conveyed by color alone (pills carry text labels).
- Reduced motion: `prefers-reduced-motion: reduce` collapses all
  transitions/animations.
- Semantic structure: `header`/`nav`/`main`/`footer` landmarks, labelled
  tables with `scope="col"`, `role="note"`/`role="alert"` on notices,
  screen-reader-only route announcements via `aria-live`.

## 10. Security boundary

- No protocol logic in JavaScript; the frontend receives only the bounded
  gui-core view models (TS mirrors in `api/types.ts`).
- The shell's 15 commands delegate verbatim to gui-core; the only shell-side
  I/O is reading explicitly chosen files (artifact triples, ballot packages,
  anchor artifacts) and writing the archive through gui-core's atomic
  writer.
- No secrets anywhere: no credential fields in state, settings, or storage;
  only a theme preference and two directory paths are persisted in
  `localStorage`.
- Strict CSP in both `index.html` and `tauri.conf.json`
  (`default-src 'self'`, no remote origins, no inline styles/scripts);
  `withGlobalTauri: false`.
- gui-core keeps its 5A2 guarantees; its security suite (7 tests, including
  the forbidden-dependency audit, now permitting serde by design) passes.
